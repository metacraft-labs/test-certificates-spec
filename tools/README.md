# Authoring tools

> **Nothing in this directory is normative, and no implementation of the
> standard is expected to read, port or invoke any of it.**
>
> Conformance is defined by [`vectors/`](../vectors), which is plain data with
> no runner. Each implementation writes its own thin walker in its own
> language. Where a tool here and the prose disagree, **the prose wins and the
> tool is a bug.**

These exist for one reason: the vectors have to be checkable and re-derivable
by anyone who suspects they were fabricated. A vector suite nobody can audit is
the thing this repository exists to replace.

| Tool | What it is for |
| ---- | -------------- |
| `reference_serializer.py` | Canonical payload from a `fields.json`, written against Canonical-Payload.md. Checks the hand-derived bytes in `vectors/payload/*/canonical.txt`. |
| `reference_content_id.py` | The three Content-Id.md algorithms from a list of entries, in plain Python. The `git-tree-*` ids are built from git's object format by hand, never by asking git. Checks `vectors/content/*/expected.json`. |
| `reference_verifier.py` | The generic half of Verification.md — framework filtering, authenticity, VCS/platform/scope, coverage as a union — producing the three-valued outcome. |
| `ssh_sig.py` | Thin wrapper over `ssh-keygen -Y sign` / `-Y verify`, and the armor ⇄ base64 conversion. |
| `regenerate.py` | Re-derives every signature and rebuilds `vectors/index.json`. Idempotent; `--check` fails if anything would change. |
| `check.py` | Runs the reference tools over the whole suite, including exact two-blob note merge bytes, reports and repeated-merge stability. |
| `walk-vectors.sh` | Walks all six groups with **POSIX shell, `jq`, `ssh-keygen`, `git` and `sha256sum` only**. |
| `corruption-demo.sh` | Damages one byte at a time and asserts the checks go red. |

## Running them

```sh
python3 tools/check.py             # reference checks, all groups
python3 tools/check.py payload     # one group
sh tools/walk-vectors.sh           # the language-agnostic walk
sh tools/corruption-demo.sh        # prove the suite detects its own corruption
python3 tools/regenerate.py --check
```

Requirements: Python 3.11+ (for `tomllib`), `jq` 1.6+ (for `@base64d` and
`--rawfile`), OpenSSH 8.0+ (for `ssh-keygen -Y`), git 2.29+ (for
`--object-format=sha256`) and `sha256sum`. Nothing else, and no packages.

## Why the payload bytes are checked and not generated

`vectors/payload/*/canonical.txt` was derived by hand from
Canonical-Payload.md. `reference_serializer.py` was then written separately
from the same document, and `walk-vectors.sh` contains a third derivation as a
`jq` program. All three agree.

That ordering matters. A `canonical.txt` generated by a serializer records only
what that serializer does; it is worthless as a specification, because a bug in
the serializer becomes a requirement. Checking a hand-derived byte sequence
against two independent serializers is a real test of the prose, and it has
already caught disagreements — see the "Ambiguities this suite closed" table in
[`vectors/README.md`](../vectors/README.md).

The content ids follow the same discipline with different roles. The
`git-tree-*` ids in `vectors/content/*/expected.json` were derived with git
itself — objects written with `git hash-object -w`, staged with
`git update-index --index-info`, and the scoped ids built with the Content-Id.md
§4.1 recipe verbatim. The `manifest-v1-sha256` ids were derived twice, once in
Python and once with `printf` and `sha256sum`, and agreed.
`reference_content_id.py` then checks all of them without git, by building the
objects by hand, and `walk-vectors.sh` re-derives them with git and
`sha256sum`. Nothing generates `expected.json` from the code that checks it.

The store paths in `vectors/store/*/expected-path.txt` were written from each
case's `canonical.txt` — a copy of a hand-derived `payload/` vector — with
`sha256sum` and the content id split at its first `:` by hand, before any tool
read them. `check.py` then rebuilds each payload from the parsed
`certificate.toml`, however non-canonical, and hashes it in Python;
`walk-vectors.sh` hashes `canonical.txt` with `sha256sum` and ties it to the
certificate by byte comparison or by verifying its signature with `ssh-keygen`
— except for `store/signed-non-canonical-no-block`, which is neither canonical
nor signed, and which it reports as resting on `check.py`'s TOML
reconstruction rather than counting as checked.

Signatures are the exception. They cannot be authored by hand, so
`regenerate.py` produces them — over the hand-derived bytes wherever a case
has them (`signature/` and `store/`), and editing only the signature `value` in
a store certificate so its deliberately non-canonical rendering survives —
deterministically, so re-running it over unchanged inputs is a no-op.

The notes in `vectors/notes/` were assembled by hand from the same
hand-derived payloads: each `note.txt`, `add.txt` and `expected-note.txt` is
delimiter lines and copies of `vectors/payload/*/canonical.txt`, plus one
record written by hand for `escaped-newline` and one truncated by hand for
`corrupt-middle`; `regenerate.py` then fills in only the signature `value`s,
over the bytes before each signature table. `check.py` re-reads every note
with a TOML parser, rebuilding each payload from the parsed fields, and runs a
reference writer over each writer case; `walk-vectors.sh` splits the notes
with `awk` and recognises records by a line grammar of the canonical form,
with no TOML parser at all.

The `notes/merge-*` expected blobs are hand-assembled from the published base,
with each expected addition or replacement selected according to Transport
§3.1. `check.py` implements that rule over parsed TOML; `walk-vectors.sh`
implements it independently over the canonical line grammar. Both check exact
bytes, diagnostic categories, and a repeated merge that must not grow the
note. The corruption demo alters expected bytes and removes a conflict report
to prove both requirements are checked.
